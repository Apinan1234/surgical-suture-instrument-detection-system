## บทพูดทีละหน้า

### หน้าที่ 1 — Section Header: Web Application Demonstration
**บทพูด:** "ต่อไปเป็นส่วนสาธิตเว็บแอปพลิเคชันครับ จะพาดูสี่ขั้นตอนหลักของการใช้งานจริง ตามด้วยภาพรวมว่าระบบวิ่งอยู่บนโครงสร้างอะไร"

### หน้าที่ 2 — 1. สกัดเฟรม (Extract Frames)
**บทพูด:** "หน้าจอนี้คือขั้นสกัดเฟรมจากวิดีโอครับ ระบบมีโหมด Adaptive ที่ผู้ใช้แค่กำหนดว่าอยากได้กี่เฟรม ไม่ต้องรู้ความยาววิดีโอเอง แล้วมีตัวกรองภาพซ้ำกับภาพเบลออัตโนมัติด้วย ในตัวอย่างนี้วิดีโอยาว 11.8 วินาที มี 355 เฟรม ระบบคัดเหลือ 11 เฟรมที่กระจายตัวดีที่สุดให้ครับ"

### หน้าที่ 3 — 2. ตรวจจับ (Detect)
**บทพูด:** "ขั้นตรวจจับครับ เลือกได้ทั้งโมเดลในเครื่องหรือ Roboflow Cloud โดยฝั่งคลาวด์มีปุ่มยืนยันก่อนเรียกทุกครั้ง ในภาพนี้กำลังโหลดโมเดลรุ่น 5 คลาสซึ่งเป็นรุ่นที่ใช้ตอนถ่ายภาพสาธิต ปัจจุบันมีโมเดลที่ดีกว่าใช้งานจริงแล้วคือรุ่น 9 คลาส mAP50 0.716 ซึ่งเป็นตัวที่รายงานผลในช่วงถัดไปครับ"

### หน้าที่ 4 — 3. กำกับข้อมูล (Annotate)
**บทพูด:** "หน้ากำกับข้อมูล หัวใจของเว็บแอปครับ กรอบเส้นประคือสิ่งที่ระบบเสนอมาแต่ยังไม่ยืนยัน กดยืนยันทั้งหมดหรือแก้ทีละกล่องก็ได้ และมีฟีเจอร์ interpolate ที่ช่วยเดากรอบเฟรมระหว่างกลางให้อัตโนมัติ ไม่ต้องวาดใหม่ทุกเฟรมครับ"

### หน้าที่ 5 — 4. ส่งออก (Export)
**บทพูด:** "ขั้นสุดท้ายคือส่งออกครับ จุดเด่นคือ export ได้ทั้งสามรูปแบบ detect segment และ pose จากข้อมูลกรอบชุดเดียวกัน โดยระบบแปลงให้อัตโนมัติ ทำให้ใช้ชุดข้อมูลเดียวไปเทรนโมเดลได้หลายแบบ พร้อมตั้งสัดส่วน train val test และ augmentation ได้เองก่อนดาวน์โหลดครับ"

### หน้าที่ 6 — System Framework
**บทพูด:** "ก่อนพูดเรื่อง Infrastructure ขอให้ดูภาพนี้ก่อนครับ ระบบจริงๆ มีแค่บริการเดียว ไม่ใช่สามบริการแยกกัน — Frontend เป็นไฟล์ static ที่ Server ตัวเดียวกันเสิร์ฟให้ ไม่มีการเรียกข้ามเครือข่ายเลย และไม่มีฐานข้อมูลจริง ใช้ไฟล์ state.json แทน ซึ่งเป็นการตัดสินใจตั้งใจครับ"

### หน้าที่ 7 — Infrastructure (Frontend / Server / Database Service)
**บทพูด:** "ขอพูดตรงๆ ว่าตอนนี้ยังไม่ได้ deploy ขึ้นเซิร์ฟเวอร์จริง รันอยู่บนเครื่อง local เท่านั้น แต่มีแผนกับ config พร้อมใช้แล้วจริงๆ ครับ ถ้าจะ deploy จะใช้ VPS แบบ CPU-only ธรรมดา ยังไม่เจาะจงผู้ให้บริการ ส่วน Database ไม่มีเลยครับ ไม่มี MongoDB เพราะใช้ state.json แทนโดยตั้งใจ และเคยใช้ Cloudflare Tunnel สร้างลิงก์ชั่วคราวไว้สาธิตเท่านั้น ไม่ใช่แผน deploy จริงครับ"

### หน้าที่ 8 — Analytics: AI-Assist Accept Rate
**บทพูด:** "หน้า Analytics ครับ ภาพนี้ถ่ายสดวันนี้เลย ตัวเลขเดิมเคยมีบั๊กจริง อ่านได้เกือบห้าพันเปอร์เซ็นต์ เพราะตัวหารกับตัวตั้งนับข้อมูลคนละชุดกัน ซึ่งแก้ไปแล้วตั้งแต่กลางเดือน ตอนนี้ตัวเลขที่ถูกต้องคือรับข้อเสนอไป 57 ครั้ง ยืนยันใช้จริง 19 กล่อง คิดเป็น 33.3% ครับ"

### หน้าที่ 9 — Analytics: Detections by Class
**บทพูด:** "ตารางนับกรอบต่อคลาสในชุดข้อมูลสดของเว็บแอปครับ finger เยอะที่สุดเพราะติดอยู่แทบทุกเฟรมที่มีมือเข้าฉาก ส่วน needle กับ Stitch Scissors ยังน้อยอยู่ ซึ่งเป็นข้อจำกัดที่จะพูดถึงอีกครั้งในส่วนผลการทดลองครับ"

### หน้าที่ 10 — Section Header: Results Summary
**บทพูด:** "ต่อไปเป็นส่วนสรุปผลการดำเนินงานครับ จะเริ่มจากตัวชี้วัดที่ใช้ ก่อนไปดูตัวเลขจริง"

### หน้าที่ 11 — สถิติของชุดข้อมูล (Dataset Statistics)
**บทพูด:** "สถิติของชุดข้อมูลที่ใช้เทรนครับ รวม 2,190 ภาพ เกือบ 23,000 กรอบ จะเห็นว่าข้อมูลไม่สมดุลกันมาก finger มีเกือบหมื่นกรอบ แต่ Stitch Scissors มีแค่ 29 กรอบทั้งชุด ซึ่งเป็นข้อจำกัดที่พวกเรารู้ตัวครับ"

### หน้าที่ 12 — ตัวชี้วัดที่ใช้: mAP50 vs mAP50-95
**บทพูด:** "ก่อนดูผลการทดลอง ขออธิบายตัวชี้วัดสักครู่ครับ mAP50 คือความแม่นที่เกณฑ์ IoU ผ่อนปรน แค่ 0.50 ตอบแค่ว่าเจอวัตถุไหม ส่วน mAP50-95 เข้มกว่ามาก เพราะเฉลี่ยตั้งแต่ 0.50 ถึง 0.95 จึงวัดว่ากรอบวางตำแหน่งแม่นแค่ไหน สองค่านี้ไม่ได้ขยับไปด้วยกันเสมอ ซึ่งจะเห็นในตารางถัดไปครับ"

### หน้าที่ 13 — ตัวอย่างจริง: IoU 0.50 vs 0.95
**บทพูด:** "ขอยกตัวอย่างจริงครับ ตอนเพิ่มความละเอียดภาพจาก 640 เป็น 960 พิกเซล ถ้าดูแค่ mAP50 แทบไม่ต่างกันเลย จะสรุปผิดว่าไม่ช่วยอะไร แต่พอดู mAP50-95 กลับขึ้นชัดเจน แปลว่ากรอบวางตำแหน่งแม่นขึ้นจริง แถม recall ของ needle ซึ่งเป็นวัตถุเล็กที่สุดก็ขึ้นด้วย นี่คือเหตุผลที่พวกเรายังเลือกใช้ 960 ทั้งที่ mAP50 ไม่ขึ้นครับ"

### หน้าที่ 14 — ⚠️ ข้าม (ไม่ใช่เนื้อหาสไลด์จริง ดูคำเตือนต้นไฟล์)

### หน้าที่ 15 — Model Result: Validation split / Benchmark comparison
**บทพูด:** "ตารางเทียบผลบน validation split ครับ baseline9-reannot คือโมเดลที่ใช้ชุดข้อมูล re-annotated ตัวเลขดีขึ้นกว่า aug960 เล็กน้อย แต่เทียบทางสถิติตรงๆ ไม่ได้เพราะแบ่ง split กันคนละชุด เหตุผลที่ดีขึ้นเป็นเชิงผลิตภัณฑ์ ซึ่งจะอธิบายต่อไปครับ"

### หน้าที่ 16 — Model Result: per-class metrics — aug960
**บทพูด:** "ผลรายคลาสของ aug960 บนชุดทดสอบครับ จะเห็นว่า needle ยังเป็นคลาสที่อ่อนที่สุดชัดเจน"

### หน้าที่ 17 — Model Result: per-class metrics — baseline9-reannot
**บทพูด:** "ผลรายคลาสของ baseline9-reannot ครับ Stitch Scissors ดูดีขึ้นมากแต่มีแค่ 3 ภาพในชุดทดสอบ ตัวเลขจึงแกว่งง่าย ไม่ควรอ่านเป็นข้อสรุปที่มั่นคง ส่วน needle ยังอ่อนที่สุดเหมือนเดิม ยืนยันว่าเป็นปัญหาจริงครับ"

### หน้าที่ 18 — การทดลอง balance กรอบคลาส finger ด้วยการสุ่ม
**บทพูด:** "ชุดข้อมูลไม่สมดุลมาก พวกเราจึงทดลองสี่แบบว่าควรจัดการยังไงดี ผลคือแบบที่ไม่ทำอะไรเลยชนะครับ การสุ่มลดภาพที่มี finger กลับแย่ที่สุด ตกไปถึง 18 จุด เพราะภาพที่มี finger เยอะมักมีคลาสอื่นติดอยู่ด้วย พอสุ่มตัดภาพออกเลยตัดตัวอย่างคลาสอื่นทิ้งไปพร้อมกันครับ"

### หน้าที่ 19 — ข้อมูล re-annotated เทียบกับ Roboflow เดิม
**บทพูด:** "แผ่นนี้ตอบว่าข้อมูล re-annotated ดีกว่าข้อมูลเดิมจาก Roboflow แค่ไหนครับ ขอเรียนตรงๆ ว่าผลต่างไม่เยอะและไม่ได้ดีขึ้นทุกด้าน mAP50 กับ recall ขึ้นเล็กน้อย แต่ mAP50-95 กลับลดลงเล็กน้อย สิ่งที่เปลี่ยนจริงคือเพิ่มภาพเกือบ 300 ภาพ เพิ่มคลาสใหม่สองคลาส และแบ่งข้อมูลใหม่แบบ stratified ครับ"

### หน้าที่ 20 — เหตุผลที่ baseline9-reannot ดีกว่า aug960
**บทพูด:** "สองเหตุผลหลักครับ อย่างแรกคือข้อมูลเพิ่มขึ้นและมีคุณภาพขึ้นจากการ re-annotate อย่างที่สองคือการแบ่งชุดข้อมูลใหม่แบบ stratified ที่ดูแลคลาสหายากเป็นพิเศษ ทำให้ผลที่วัดได้น่าเชื่อถือกว่าการแบ่งแบบสุ่มธรรมดาของ Roboflow เดิมครับ"

### หน้าที่ 21 — สรุปผลและข้อเสนอแนะ
**บทพูด:** "สรุปครับ ระบบทำได้ตามเกณฑ์ที่ตั้งไว้ และเว็บแอปเป็นเครื่องมือที่ใช้งานจริงตลอดโครงงาน ไม่ใช่แค่ของประกอบ ข้อเสนอแนะที่สำคัญที่สุดคือเก็บข้อมูลเพิ่มสำหรับคลาสหายากอย่าง needle และ Stitch Scissors ส่วนเป้าหมายปลายทางคือโมเดลวิเคราะห์ลำดับเหตุการณ์เชิงเวลาครับ"
