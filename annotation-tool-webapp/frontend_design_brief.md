# Rare Class Labeler — Frontend Design Brief

> เอกสารนี้เขียนขึ้นเพื่อส่งต่อให้เครื่องมือออกแบบภายนอก (Claude Design / Google AI Studio หรือเทียบเท่า)
> ใช้ออกแบบหน้าเว็บและ UI component **เฉพาะฝั่ง Frontend เท่านั้น** ผลลัพธ์การออกแบบ (โค้ด
> HTML/CSS/JS) จะถูกนำกลับมาให้ Claude Code ต่อเข้ากับระบบจริงฝั่ง backend (โมเดลตรวจจับ, การ
> ประมวลผลวิดีโอ, การ export ชุดข้อมูล ฯลฯ) ในขั้นตอนถัดไป — **เอกสารนี้จึงบอกแค่ว่าแต่ละส่วนของหน้า
> เว็บ "ทำหน้าที่อะไร" และ "แสดงข้อมูลอะไร" เท่านั้น ไม่ได้กำหนดสี ฟอนต์ หรือเลย์เอาต์ตายตัว —
> ปล่อยให้เป็นดุลยพินิจของการออกแบบทั้งหมด**

---

## 1. ภาพรวมโปรดักต์และผู้ใช้งาน

**Rare Class Labeler** เป็นเว็บทูลสำหรับงานตรวจจับอุปกรณ์การเย็บแผลในวิดีโอผ่าตัด (สัตวแพทย์)
ด้วยโมเดล YOLO ที่เทรนไว้แล้ว (9 คลาส) จุดประสงค์หลักคือช่วยผู้ใช้ **ดึงเฉพาะเฟรมของคลาสที่หายาก**
(เช่น `needle` ที่มีตัวอย่างในชุดข้อมูลน้อยกว่าคลาสอื่นมาก) ออกมาเป็นชุดข้อมูลใหม่ เพื่อนำไป annotate
เพิ่มและแก้ปัญหาข้อมูลไม่สมดุลระหว่างคลาส

**Flow การใช้งานคือ**: อัปโหลดวิดีโอ → ระบบตรวจจับให้อัตโนมัติ → ดูผลลัพธ์ + เลือกคลาสที่ต้องการ →
ดาวน์โหลดชุดข้อมูล

**ผู้ใช้งานเป็นใคร**: คนไทย ไม่จำเป็นต้องมีความรู้ด้าน AI/Machine Learning มาก่อน โปรเจกต์รุ่นก่อนหน้า
เคยถูกอาจารย์ตีกลับเพราะ **"ใช้ยาก ไม่อัตโนมัติพอ"** — เป้าหมายของเวอร์ชันนี้คือแก้ปัญหานั้นโดยตรง
ดังนั้นโทนของดีไซน์ควรสื่อถึง: **เรียบง่าย, อัตโนมัติ, น่าเชื่อถือ** ไม่ใช่หน้าตาแบบ "AI tool" ที่ดูซับซ้อน
หรือน่ากลัวสำหรับคนทั่วไป

---

## 2. Flow การใช้งาน — ผู้ใช้ทำได้แค่ 3 อย่างเท่านั้น

นี่คือข้อกำหนดที่สำคัญที่สุดของทั้งโปรดักต์ ยืนยันแล้วหลายรอบ **ห้ามมี action อื่นนอกจากนี้**:

1. **อัปโหลดวิดีโอ** — action บังคับเดียว หลังจากนี้ระบบทำงานอัตโนมัติทั้งหมด (โหลดโมเดล, สุ่มเฟรม,
   ตรวจจับ) ไม่มีขั้นตอนตั้งค่าใด ๆ ก่อนเริ่ม ไม่มีปุ่ม "เริ่มประมวลผล" แยกต่างหาก
2. **เลือกคลาสที่จะเก็บ** — จาก grid ผลลัพธ์ที่ปรากฏหลังประมวลผลเสร็จ
3. **ดาวน์โหลด** — ไฟล์ zip ของชุดข้อมูลที่กรองแล้ว

มี 2 ฟีเจอร์เสริมที่เก็บไว้เป็นทางลัด/ความสะดวก (ไม่ใช่ action บังคับ): ปุ่มตัวอย่างวิดีโอกดเดียวรัน
(Examples) และประวัติการรันก่อนหน้าในเซสชันนั้น (History)

---

## 3. ส่วนประกอบของหน้าเว็บ (Components) — อธิบายเชิงหน้าที่

แต่ละส่วนด้านล่างนี้คือสิ่งที่ต้องมีอยู่ในหน้าเว็บ อธิบายว่า **ทำหน้าที่อะไร แสดงข้อมูลอะไร และมี state
ไหนบ้าง** — รูปแบบภาพ ไอคอน สี ฟอนต์ เลย์เอาต์ เป็นอิสระทั้งหมด ให้ออกแบบใหม่จากศูนย์

### 3.1 Masthead / หัวเว็บ
- ชื่อโปรดักต์ + tagline สั้น ๆ ที่สื่อว่า "อัปโหลดอย่างเดียว ระบบจัดการที่เหลือให้"

### 3.2 ช่องอัปโหลดวิดีโอ (Upload)
- รองรับทั้งลากไฟล์มาวาง (drag-and-drop) และคลิกเพื่อเลือกไฟล์
- **ต้องมีพรีวิววิดีโอที่อัปโหลดจริง** (เล่นได้จริงในเบราว์เซอร์) ทันทีที่เลือกไฟล์
- รองรับไฟล์วิดีโอขนาดใหญ่/ยาว (นี่คือจุดที่เวอร์ชันต้นแบบเคยมีบั๊ก — ฝั่งดีไซน์ไม่ต้องกังวลเรื่องนี้ แต่
  ควรออกแบบ state "กำลังอัปโหลด/กำลังโหลดพรีวิว" ไว้ด้วยเผื่อไฟล์ใหญ่ใช้เวลา)
- States: ว่าง (ยังไม่มีไฟล์) / กำลังลากไฟล์ผ่าน (drag-over) / มีไฟล์แล้ว+พรีวิวแสดง / ต้องมีปุ่มหรือ
  ลิงก์ให้ "เลือกไฟล์อื่น" เพื่อเริ่มใหม่

### 3.3 ตัวแสดงสถานะประมวลผลอัตโนมัติ (Processing indicator)
- ปรากฏขึ้นทันทีที่อัปโหลดเสร็จ **ไม่มีปุ่มให้กดเริ่ม** — สื่อว่าระบบทำงานเองทันที
- ต้องมี progress bar หรือองค์ประกอบที่สื่อความคืบหน้าเชิงตัวเลข (0-100%)
- ต้องมีข้อความสถานะที่เปลี่ยนไปเรื่อย ๆ ระหว่างรอ (เช่น "กำลังโหลดโมเดล...", "กำลังตรวจจับวัตถุ...",
  "กำลังประกอบวิดีโอผลลัพธ์...") เพราะการประมวลผลจริงอาจใช้เวลานาน (วิดีโอยาวหลายนาทีบน CPU) —
  ผู้ใช้ต้องรู้สึกว่าระบบยังทำงานอยู่ ไม่ใช่ค้าง

### 3.4 วิดีโอผลลัพธ์ (Output video player)
- เล่นวิดีโอที่มีกรอบ (bounding box) วาดทับลงบนวัตถุที่ตรวจพบ พร้อมชื่อคลาส
- ควรเล่นอัตโนมัติ/วนซ้ำได้ เพื่อให้ผู้ใช้เห็นผลลัพธ์ทันทีโดยไม่ต้องกด play เอง
- วิดีโอนี้แสดง**ทุกคลาส**ที่ตรวจพบ ไม่ถูกกรองตามที่เลือกในขั้นถัดไป (ใช้เพื่อ "เช็คว่าโมเดลวาดกรอบถูกที่
  ไหม" แทนการต้องมานั่งเลื่อนดูภาพทีละภาพ)

### 3.5 Grid ผลลัพธ์ (Results grid) — ส่วนสำคัญที่สุด
- แสดงเป็น grid ของ "การ์ด/tile" — **หนึ่ง tile ต่อหนึ่งคลาสที่ตรวจพบจริงในวิดีโอนั้น** จำนวน tile ไม่คงที่
  (ขึ้นกับว่าวิดีโอนั้นมีคลาสอะไรบ้าง ไม่ใช่ตายตัว 9 อันเสมอไป — แต่ตัวอย่างเนื้อหาด้านล่างให้ใช้ 9 คลาส
  จริงของโมเดลเป็นตัวอย่างเนื้อหาไปก่อน)
- แต่ละ tile ต้องมี:
  - **รูปตัวแทน (thumbnail)** — ครอปมาจากเฟรมจริงที่ตรวจพบวัตถุนั้น ๆ (ไม่ใช่ไอคอน ไม่ใช่รูปตกแต่ง)
  - **ชื่อคลาส** (ข้อความภาษาอังกฤษ เป็นชื่อทางเทคนิคที่ตายตัว — ดูรายชื่อจริงด้านล่างข้อ 4)
  - **จำนวนที่พบ** (ตัวเลข เช่น "94 เฟรม")
  - **Checkbox หรือ toggle** ให้เลือกว่าจะรวมคลาสนี้ในการดาวน์โหลดหรือไม่ (ค่าเริ่มต้น: เลือกไว้ทั้งหมด)
- ควรมีปุ่ม/ลิงก์ช่วยเลือกด่วน "เลือกทั้งหมด" / "ไม่เลือกเลย"
- ต้องมีจุดแสดงสรุปว่าตอนนี้เลือกไว้กี่คลาส
- **โอกาสทางดีไซน์**: คลาส `needle` คือคลาสหายากที่เป็นเหตุผลหลักที่โปรดักต์นี้ถูกสร้างขึ้นมา (จำนวนที่
  พบจะน้อยกว่าคลาสอื่นมากเสมอ) ควรมีวิธีทำให้ผู้ใช้สังเกตเห็นคลาสที่จำนวนน้อยได้ง่าย (เช่น ป้ายเตือน,
  การเน้น, หรือวิธีอื่นตามดุลยพินิจการออกแบบ) — นี่คือจุดเด่นของโปรดักต์ ไม่ใช่รายละเอียดเล็กน้อย

### 3.6 ส่วนดาวน์โหลด (Download)
- ปุ่มดาวน์โหลดหลัก (ดาวน์โหลดไฟล์ .zip)
- คำอธิบายสั้น ๆ ว่าในไฟล์ zip มีอะไรบ้าง: ภาพต้นฉบับ + ไฟล์ label (เฉพาะคลาสที่เลือก), โฟลเดอร์ภาพที่
  วาดกรอบไว้ให้ตรวจสอบด้วยตา, ไฟล์บันทึกว่า label ครอบคลุมคลาสอะไรบ้าง
- ปุ่มดาวน์โหลดควรถูกปิดใช้งาน (disabled) ถ้าผู้ใช้ไม่เลือกคลาสไว้เลยสักอัน

### 3.7 ตัวอย่างเริ่มต้นด่วน (Examples)
- Tile/การ์ดตัวอย่างวิดีโอที่กดแล้วรันทั้ง flow ให้ทันทีแบบคลิกเดียว (สำหรับสาธิต/ทดลองใช้แบบไม่ต้องหา
  ไฟล์วิดีโอเอง)

### 3.8 ประวัติการใช้งาน (History)
- รายการของการรันก่อนหน้าในเซสชันนั้น (ชื่อวิดีโอ, เวลา, คลาสที่เคยเลือกไว้)
- กดที่แถวประวัติเพื่อโหลดค่ากลับมาใช้ซ้ำ

## 4. เนื้อหาจริงที่ต้องใช้ในการออกแบบ (ห้ามใช้ข้อมูลสมมติแทน)

**รายชื่อ 9 คลาสจริงของโมเดล (เรียงตามลำดับจริงของ checkpoint)** — ใช้เป็นเนื้อหาตัวอย่างใน Results
grid เพื่อให้ออกแบบขนาด/การตัดบรรทัดของข้อความได้ตรงกับของจริง:

```
Stitch Scissors, Tip_forcep, Tip_needle_holder, finger, forcep, hand, needle, needle_holder, wound
```

- ข้อความ UI ทั้งหมด (ป้าย, ปุ่ม, คำอธิบาย) เป็น**ภาษาไทย** ยกเว้นชื่อคลาสที่เป็นภาษาอังกฤษตายตัวตามที่
  โมเดลกำหนด (ห้ามแปลชื่อคลาสเป็นไทย)
- ต้องรองรับการแสดงผลภาษาไทยที่ถูกต้อง (สระ วรรณยุกต์ ไม่ล้น/ไม่ซ้อนผิดตำแหน่ง)
- `needle` ควรได้จำนวนตัวอย่างที่น้อยที่สุดในเนื้อหาตัวอย่าง (สื่อถึงปัญหาคลาสหายากที่โปรดักต์นี้แก้)

## 5. ขอบเขตที่ไม่ต้องทำ (Out of scope)

เพื่อไม่ให้เสียเวลาไปกับส่วนที่ไม่ต้องมี:

- **ไม่ต้องทำระบบจริงเบื้องหลัง** — ไม่ต้องเชื่อมโมเดล AI จริง ไม่ต้องประมวลผลวิดีโอจริง ไม่ต้องสร้างไฟล์
  ดาวน์โหลดจริง ทำแค่ UI/UX และการจำลอง interaction เท่านั้น ระบบจริงจะทำโดย Claude Code ในขั้นถัดไป
- **ห้ามมีส่วนตั้งค่าเพิ่มเติมใด ๆ** — ห้ามมี dropdown เลือกโมเดล, ห้ามมี slider ปรับค่า confidence/IoU,
  ห้ามมีช่องกรอกชื่อคลาสอิสระ, ห้ามมีอะไรที่ทำให้ผู้ใช้ต้อง "ตั้งค่า" ก่อนอัปโหลด — ตัดออกจากโปรดักต์นี้
  โดยตั้งใจแล้ว อย่าใส่กลับเข้ามาแม้จะดูเหมือนเป็นฟีเจอร์ที่มีประโยชน์
- **ไม่ต้องยึดสี/ฟอนต์/เลย์เอาต์จากต้นแบบเดิม** — มีต้นแบบทดลอง (mockup) ที่ทำงานได้ครบตาม flow นี้แล้ว
  ที่ `mockup/index.html` ในโปรเจกต์เดียวกัน ใช้อ้างอิงได้แค่เรื่อง**พฤติกรรม/การทำงาน** เท่านั้น — ดีไซน์
  ภาพของต้นแบบนั้นถูกประเมินแล้วว่ายังไม่ดีพอ จุดประสงค์ของเอกสารนี้คือให้ออกแบบใหม่ทั้งหมด ไม่ใช่ปรับ
  ต้นแบบเดิม

## 6. หมายเหตุทางเทคนิคสำหรับทีมพัฒนา (ไม่บังคับสำหรับผู้ออกแบบ)

การ implement จริงจะเป็น HTML/CSS/JS อิสระ (ไม่ผูกกับ framework เฉพาะทางอย่าง Gradio) เชื่อมกับ
backend ฝั่ง Python ภายหลัง ดังนั้นผลลัพธ์การออกแบบที่เป็นโค้ด HTML/CSS/JS มาตรฐานทั่วไปจะนำมาต่อยอด
ได้โดยตรง ไม่มีข้อจำกัดพิเศษด้าน component ใด ๆ ที่ต้องระวังในขั้นตอนออกแบบ
