## วิเคราะห์ช่องโหว่ — ปัญหาที่เจอในลิสต์ฟังก์ชันเดิมของผู้ใช้ และวิธีแก้ของแต่ละข้อ

1. **พรีวิววิดีโอไฟล์ใหญ่พังจริง ยืนยันแล้วในต้นแบบตอนนี้** ทดสอบสด ๆ ในเซสชันนี้: อัปโหลดไฟล์จริง
   202MB (`WIN_20260525_14_47_12_Pro_muted.mp4`) เข้าแอปของ `yolo_wv` แล้วเจอ
   `h11._util.LocalProtocolError: Too little data for declared Content-Length` +
   `ConnectionResetError` ทันทีที่เบราว์เซอร์ยิง byte-range request จริง (ที่ทับซ้อน/พร้อมกันหลายอัน)
   — ยิง range request เดี่ยว ๆ ผ่าน curl กลับไม่พังเลย แปลว่าเป็นปัญหาเฉพาะตอนเบราว์เซอร์สตรีมวิดีโอจริง
   ไม่ใช่ที่ตัวไฟล์หรือ codec H.264 นี่คือบั๊กที่รู้จักกันของ Windows `ProactorEventLoop` ชนกับการตอบ
   range-request ไฟล์ใหญ่ของ Starlette เนื่องจาก "ใส่วิดีโอยาวได้" คือข้อกำหนดข้อ 1 โปรเจกต์ใหม่ต้อง
   แก้เรื่องนี้ให้ถูกต้องตั้งแต่แรก — ดู Phase 1
2. **วิดีโอยาว + ตรวจจับทุกเฟรมด้วย CPU ช้า ไม่มี feedback — และไม่มีขั้นตอนที่ผู้ใช้ต้องกดเองมาคั่นระหว่าง
   รอด้วย** วัดไว้แล้วในโปรเจกต์อื่นใน workspace นี้: median ~140ms/เฟรมบน CPU
   (`results_960/inference_benchmark.md`) → คลิป 10 นาที 30fps จะใช้เวลาตรวจจับ 40+ นาที เนื่องจาก
   อัปโหลดคือ action บังคับเดียว แถบแสดงความคืบหน้ายิ่งสำคัญกว่าเดิม ไม่ใช่น้อยลง วิธีแก้: ต่อ
   `gr.Progress()` แบบจริงจังผ่าน closure `progress_callback(frame_idx, n_frames)` แบบเดียวกับที่
   `yolo-frame-miner/web/app.py`'s `run_mine()` ใช้อยู่แล้วและใช้งานได้จริง
3. **การอัปโหลดโมเดลไม่ใช่ attack surface ของโปรดักต์นี้อีกต่อไป — วิธีลดความเสี่ยง RCE จึงเปลี่ยนรูปแบบ
   ตาม** การอัปโหลด `.pt` ตามใจชอบแล้วโหลดด้วย `ultralytics.YOLO(path)` คือช่องโหว่ CVE-2025-32434
   (deserialize ไม่ปลอดภัยผ่าน `torch.load`); แผนเดิมลดความเสี่ยงนี้ด้วย path-jail (รูปแบบ
   `_resolve_model_path`) สำหรับฟีเจอร์อัปโหลด **ตอนนี้ฟีเจอร์อัปโหลดถูกตัดออกแล้ว** (การปรับ workflow
   2026-08-23 — ไม่มี UI เลือกโมเดลเลย) ดังนั้น path-jail ไม่มีอะไรให้ป้องกันแล้ว และถูกตัดออกจากขอบเขต
   ทั้งหมด — สร้างมันขึ้นมาสำหรับฟีเจอร์ที่ไม่มีอยู่จริงจะเป็นความซับซ้อนที่ไม่จำเป็นแบบที่ผู้ใช้ปฏิเสธมาตลอด
   ในที่อื่น ๆ สิ่งที่ยังคงไว้ เป็นการป้องกันชั้นที่สองแบบราคาถูกสำหรับ checkpoint เดียวที่แอปนี้โหลดจริง:
   ตั้ง `ULTRALYTICS_SAFE_LOAD` ก่อน import ultralytics ใด ๆ ตามรูปแบบที่
   `yolo-frame-miner/web/app.py` เลือกทำเช่นกัน แม้ตัวมันเองก็โหลดแค่โมเดล bundle เดียวไม่มีช่องทาง
   อัปโหลดสาธารณะเหมือนกัน
4. **ห้ามเชื่อ class order แบบ index ดิบเด็ดขาด** เจอบทเรียนนี้มาแล้วอย่างเจ็บปวดในโปรเจกต์พี่น้อง —
   ลำดับ `model.names` ของแต่ละโมเดลเป็นเรื่องเฉพาะของโมเดลนั้น ต้องแปลด้วยชื่อเสมอ ห้ามอ้างอิงตำแหน่ง
   โปรเจกต์นี้จะ resolve คลาสผ่าน `frame_miner.classes.native_order(model.names)` ทุกครั้งที่โมเดล
   bundle โหลด ซึ่งตอบโจทย์ "อิงข้อมูลจริงจากโมเดล ไม่ใช่ mockup" ไปในตัว
5. **Export label เฉพาะคลาสเป้าหมาย — ยอมรับความเสี่ยงแล้ว แต่มีทางลดผลกระทบ** เวลา export key frame
   จะ label เฉพาะคลาสที่เลือกจาก grid ผลลัพธ์หลังประมวลผลเท่านั้น แม้เฟรมนั้นจะมีคลาสอื่นติดมาจริง
   ความเสี่ยงที่ยอมรับ: ถ้าเอาไปรวมกับ dataset ใหญ่แล้วเทรนแบบหลายคลาสในอนาคต วัตถุอื่นที่อยู่ในภาพจริง
   แต่ไม่มี label จะกลายเป็น false negative ทางลดผลกระทบ: ทุกครั้งที่ export จะเขียนไฟล์
   `PARTIAL_LABELS.md` พร้อมช่องข้อมูลใน `export_summary.json` ระบุชัดว่า label ครั้งนี้ครอบคลุมคลาส
   อะไรบ้าง เพื่อให้ตรวจสอบย้อนหลังได้ตอนจะเอาไปรวม dataset ส่วนโฟลเดอร์ภาพ QA ที่วาดกรอบไว้ก็ช่วยเป็น
   ตัวตรวจสอบด้วยตาอีกชั้นหนึ่ง
6. **ไม่มี dedup — ยอมรับแล้ว** ใช้แค่ sample-interval คุมความถี่ของเฟรม ไม่มีขั้นตอน phash
7. **โค้ด export/merge dataset — เอามาใช้ผ่านการติดตั้งเป็น dependency ไม่เขียนใหม่เด็ดขาด**
   `pip install -e C:\Users\USER\yolo-frame-miner` เข้า venv ของโปรเจกต์นี้เอง แล้ว import
   `frame_miner.classes`, `frame_miner.export`, `frame_miner.merge`, `frame_miner.source` ตรง ๆ
   `frame_miner.mine.mine_source()` เอง**ไม่ได้ถูกเอามาใช้ตรง ๆ** เพราะมันจะ label ทุกคลาสที่เจอเสมอ
   ซึ่งขัดกับการตัดสินใจข้อ 5 — ดังนั้น loop คัดกรอง/ขุดเฟรมของโปรเจกต์นี้เขียนขึ้นมาเอง แต่ทุกอย่างที่อยู่
   ถัดจาก "เฟรมไหนถูกเก็บไว้บ้าง" (ตัวแบ่ง split, ตัวเขียน `data.yaml`, การวางแผน/สั่ง merge) ยังเป็นโค้ด
   เดิมของ `frame_miner` ที่ verify แล้ว ไม่แตะเลย
8. **Examples กับ History ตั้งใจเก็บไว้ แม้จะเป็นการกดเพิ่มนอกเหนือกฎ "3 action"** ยืนยันชัดเจนอีกครั้งเมื่อ
   2026-08-23 หลังถามตรง ๆ: มันเป็นทางลัด/ความสะดวก ไม่ใช่ config ของการตรวจจับแบบที่ตัด
   model/threshold ออกไป จึงไม่ขัดกับ "ผู้เข้าใช้ไม่ต้องเลือก [การตั้งค่า pipeline ใด ๆ]" `gr.Examples`
   เป็นแค่ลิสต์ตัวอย่างตายตัว ไม่ใช่ "ประวัติที่ทำไปในเซสชันนี้" — ประวัติต้องมี component แยกเล็ก ๆ

   แยกต่างหาก

## Phase 5 — Frame extraction (การสุ่มเฟรม)

`backend/frame_extraction.py` — **ปรับดีไซน์แล้ว (2026-08-24)**: เดิมวางแผนไว้ว่าจะห่อ
`frame_miner.source.iter_video_frames()` ตรง ๆ แต่ค้นพบว่าฟังก์ชันนั้น `cap.grab()` (ข้ามไม่ถอดรหัส)
เฟรมที่อยู่นอก sample-interval — เหมาะกับการใช้งานของ `frame-miner` เอง (ไม่เคยเขียนวิดีโอผลลัพธ์)
แต่ใช้ไม่ได้กับที่นี่ที่ต้องถอดรหัส*ทุกเฟรม*สำหรับวิดีโอผลลัพธ์ (Phase 6) จึงเขียน generator ใหม่ที่เปิด
`cv2.VideoCapture` ครั้งเดียว ถอดรหัสทุกเฟรมในรอบเดียว (รูปแบบยกมาจาก `yolo_wv/app/utils.py`) โดยเอามา
ใช้ซ้ำแค่สูตร `frame_step = max(1, int(fps * interval_sec))` ของ `iter_video_frames()` ไม่ใช่ตัว
ฟังก์ชันเอง — ยังคงเป้าหมาย "ถอดรหัสวิดีโอเต็มรอบเดียวจบ ไม่ทำสองรอบ" ไว้ครบ ผลลัพธ์คือ
`open_frame_source(path, interval_sec=1.0) -> (VideoMeta, Iterator[ExtractedFrame])` — `VideoMeta`
(fps/n_frames/width/height/frame_step) อ่านครั้งเดียวจาก capture ตัวเดียวกันแล้วคืนค่าก่อนเริ่มวน
(เพื่อให้ Phase 6 ตั้งค่า `VideoWriter` ได้ก่อนเขียนเฟรมแรก) ส่วน `ExtractedFrame` (index/image/
timestamp_sec/is_candidate) ถูก yield ทีละเฟรมที่ถอดรหัสแล้ว ไม่มีพารามิเตอร์ progress-callback และ
ไม่มี `VideoWriter`/ffmpeg ในไฟล์นี้โดยตั้งใจ — สองอย่างนั้นเป็นหน้าที่ของ Phase 6/2 ซึ่งมี `index` และ
`meta.n_frames` อยู่แล้วจากการวน generator นี้

## Phase 6 — อะไรก็แล้วแต่ที่ต้องใช้ (ตรวจจับ, กรอง, แสดงผลลัพธ์สด และ export)

  จะเก็บภาพต้นฉบับสะอาด + ภาพสำเนาที่วาดกรอบไว้สำหรับตรวจสอบ (QA) ของ*ทุกคลาส*ที่เจอ ลงโฟลเดอร์

  (`images/`, `labels/`, `preview/`); ไฟล์ label เขียนแยกเป็นรายคลาส เพื่อให้พอผู้ใช้เลือกคลาสจาก grid
  ผลลัพธ์แล้ว ขั้นตอน export กรองเหลือเฉพาะ label ของคลาสนั้น ๆ ได้เลย
  (`frame_miner.classes.class_id_for_name()` ไม่ใช้ id ดิบจากโมเดล) โดยไม่ต้องรันตรวจจับซ้ำ ไม่มี
  ขั้นตอน dedup (ตามการตัดสินใจข้อ 6) — sample-interval เป็นตัวคุมความหนาแน่นเพียงอย่างเดียว
- **Gallery + download / export** (`backend/dataset_export.py`) — พอผู้ใช้เลือกคลาสแล้วกดดาวน์โหลด:
  เรียก `frame_miner.export.export_dataset()` กับชุด staging ที่กรองตามคลาสแล้ว (เอาตัวแบ่ง split
  แบบ largest-remainder และตัวเขียน `data.yaml` แบบ Roboflow-layout มาใช้ตรง ๆ) เขียนไฟล์
  `PARTIAL_LABELS.md` (ช่องโหว่ข้อ 5) จัดโฟลเดอร์ภาพ QA ที่วาดกรอบไว้ แล้วบีบอัดเป็น zip ให้ `gr.File`
