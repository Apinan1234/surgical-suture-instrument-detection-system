## 1.6 สะพานที่ดีที่สุดจากตัวอย่างเข้าโปรเจกต์เรา

**แผ่น 14 "Limitations of YOLO" ของตัวอย่างบอกเองว่า YOLO อ่อนกับ *กลุ่มวัตถุขนาดเล็ก* และ
*localization error ที่ปฏิบัติกับกล่องเล็กเท่ากับกล่องใหญ่*** — ซึ่งคือปัญหา `needle` ของเราเป๊ะ ๆ

สไลด์ของเราจะใช้แผ่นนี้เป็น **ทฤษฎีที่มีคนเขียนไว้ก่อน** แล้วต่อด้วย **หลักฐานที่เราวัดเอง**:
80.9% ของกรอบ needle เล็กกว่าเกณฑ์ small ของ COCO · ด้านสั้นมัธยฐาน 12.4 พิกเซล ที่ imgsz 640
→ ตั้งสมมติฐาน → เทรนซ้ำเปลี่ยน `imgsz` อย่างเดียว → needle recall 0.2435 → 0.3579

นี่คือลำดับที่ทำให้กรรมการเห็นว่างานเรา **ไม่ได้เดา** แต่ไปเจอปัญหาเดียวกับที่วรรณกรรมระบุไว้
แล้ววัดมันในบริบทของเราเอง

## 2.2c สไลด์สำรอง = เครื่องมือซ้อมจำ ไม่ใช่แค่เผื่อเหตุฉุกเฉิน

ผู้ใช้ยืนยันแนวทางนี้ชัดเจน (16 ส.ค. 2569): **สไลด์สำรองไม่ได้มีไว้แค่เปิดตอนถูกถามหน้างาน**
แต่ใช้เป็นเอกสารซ้อมพูดล่วงหน้าด้วย — อ่านสไลด์สำรองตอนซ้อมช่วยให้จำตัวเลข/เหตุผลได้แม่นขึ้น
แม้จะไม่ได้ขึ้นจอวันจริงก็ตาม เพราะฉะนั้นสไลด์สำรองต้อง:

- เขียนสมบูรณ์พอที่จะอ่านแล้วเข้าใจได้เอง ไม่ใช่แค่หัวข้อสั้น ๆ (ต่างจากสไลด์หลักที่ต้องเบา)
- อยู่รวมกันท้ายเด็ค ไม่กระจายแทรกในเนื้อหาหลัก — ให้ค้นหาได้เร็วทั้งตอนซ้อมและตอนสอบจริง
- แต่ละแผ่นควรตอบคำถามเดียวที่คาดว่าจะถูกถามให้ครบในตัวเอง

## 2.4 ข้อขัดแย้งที่ต้องตัดสิน — "ขอละเอียด" vs "สไลด์ต้องเบา"

ผู้ใช้ขอเนื้อหาละเอียดจนกรรมการที่ไม่รู้จักโปรเจกต์ตามได้ แต่ทั้งตัวอย่าง CS231n และ
assertion-evidence บอกว่าสไลด์ต้องเบา สองข้อนี้ไม่ขัดกันถ้าแยกให้ถูกที่:

> ### ความละเอียดอยู่ที่ **จำนวนสไลด์ + บทพูด + สไลด์สำรอง** ไม่ใช่ที่ความหนาแน่นของแผ่นเดียว

| ที่เก็บความละเอียด | กติกา |
|---|---|
| **จำนวนสไลด์** | หนึ่งความคิด = หนึ่งแผ่น · แตกแผ่นที่แน่นออกเป็นหลายแผ่นแทนที่จะยัด |
| **บทพูด** | รายละเอียดเชิงลึกอยู่ในบทพูด (ใส่เป็น speaker notes ใน `.pptx` ได้) |
| **สไลด์สำรอง** | ตัวเลขเต็ม ตารางเต็ม เปิดเฉพาะตอนถูกถาม |
| **บนหน้าสไลด์** | 3-5 bullet หรือภาพเดียว · ตัวอักษรไม่ต่ำกว่า 15 pt |

## 2.5 มุมมองการนำเสนอ — **นักศึกษา → อาจารย์ที่เป็นกรรมการสอบ**

**นี่คือข้อกำหนดที่คุมทุกบรรทัดในสไลด์และบทพูด** ไม่ใช่การบรรยายวิชาการ ไม่ใช่การขายของ
แต่คือนักศึกษาสามคนรายงานงานของตัวเองต่ออาจารย์ที่มาตัดสิน

| หลักการ | ทำยังไงในสไลด์ |
|---|---|
| **กรรมการไม่ได้ทำโปรเจกต์กับเรา** | ห้ามใช้ศัพท์เฉพาะของโปรเจกต์ (Label Assist, slot, filmstrip, reannot) ก่อนอธิบาย · ห้ามอ้างชื่อไฟล์ลอย ๆ โดยไม่บอกว่ามันคืออะไร |
| **กรรมการอาจไม่ได้อ่านเล่มรายงานมาก่อน** | ทุกส่วนต้องยืนได้ด้วยตัวเอง · เริ่มด้วย "ปัญหาคืออะไร" ก่อนเสมอ ไม่ใช่เริ่มด้วย "เราทำอะไร" |
| **กรรมการมาตัดสิน ไม่ได้มาเรียน** | ทุกแผ่นต้องตอบคำถาม "แล้วยังไง" ได้ — ผลนี้แปลว่าอะไร ทำไมถึงสำคัญกับโจทย์ |
| **สรรพนาม** | ใช้ **"ทีมของเรา / พวกเรา / กลุ่มของเรา"** สำหรับสิ่งที่ทำเอง · ใช้ **"ครับ/ค่ะ"** ในบทพูด · เรียกอาจารย์ว่า **"อาจารย์"** ไม่ใช่ "ท่านผู้ฟัง" |
| **ความซื่อสัตย์ได้คะแนน** | ระบุข้อจำกัดเอง**ก่อน**ที่กรรมการจะถาม · ที่ไหนผลไม่เป็นอย่างที่คาด ให้พูดว่าไม่เป็นอย่างที่คาด · ที่ไหนเคยสรุปผิดแล้วไปวัดจนพบว่าผิด ให้เล่า — นั่นคือหลักฐานว่าทีมทำงานเป็น |
| **ห้ามพูดเกินที่วัดได้** | ถ้าไม่ได้วัด ห้ามอ้าง · ทุกตัวเลขต้องชี้ไฟล์ต้นทางได้ทันทีเมื่อถูกถาม |
| **แบ่งกันพูดสามคน** | เกณฑ์ข้อ 5 ให้คะแนนรายบุคคล — แต่ละคนต้องพูดช่วงที่ตัวเอง**ตอบคำถามได้จริง** ไม่ใช่แบ่งตามจำนวนแผ่น |
| **เตรียมคำตอบไว้ในสไลด์สำรอง** | ทุกกติกา ❶-⓭ ใน §7 คือคำถามที่กรรมการถามได้จริง — ต้องมีแผ่นสำรองรองรับทุกข้อ |

**สิ่งที่ต้องไม่ทำ:** ห้ามอ่านสไลด์ออกเสียงคำต่อคำ · ห้ามข้ามสไลด์เพราะ "เดี๋ยวไม่ทัน"
(ถ้าไม่ทันแปลว่าต้องตัดสไลด์ก่อนวันสอบ) · ห้ามตอบว่า "ไม่ได้ทำ" เฉย ๆ ให้ตอบว่า
"ยังไม่ได้ทำ เพราะ… และถ้าทำจะทำแบบนี้"

# §4 · Content rules ต่อ archetype

| ประเภทสไลด์ | กติกาการเขียน |
|---|---|
| concept / overview | หัวข้อเป็นประโยคข้อสรุป + bullet 3-5 ข้อ ไม่มีย่อหน้ายาว |
| diagram สถาปัตยกรรม | ภาพเป็นตัวเอกของแผ่น ข้อความอธิบายสั้นด้านข้างหรือใต้ภาพ |
| ผลลัพธ์ (results) | กราฟ/เมทริกซ์เต็มพื้นที่ + ตัวเลขสรุป 1-2 บรรทัด + บรรทัดที่มา |
| เปรียบเทียบ (trade-off) | ตารางหรือกราฟ **ห้าม** bullet list ยาว |
| tools / tech stack | ตารางเสมอ ไม่ใช่ bullet |
| ข้อจำกัด | เป็นแผ่นของตัวเอง ไม่ยัดท้าย bullet ของแผ่นอื่น |
| ทุกภาพที่ไม่ได้ทำเอง | ต้องมี caption แหล่งที่มา |
| ทุกแผ่นที่มีตัวเลข | ต้องมีบรรทัดที่มา ระบุไฟล์ผลจริง |

## โทนการเขียน

ประโยคสั้น ตรงไปตรงมา ไม่ขายของ **ระบุข้อจำกัดในแผ่นเดียวกับที่ระบุผลสำเร็จ**
เมื่อผลไม่เป็นอย่างที่คาด ให้พูดว่าไม่เป็นอย่างที่คาด — งานนี้มีตัวอย่างแบบนั้นสองครั้ง
(augmentation ไม่ทำร้ายวัตถุเล็กอย่างที่กลัว · mAP50 ไม่ขึ้นตอนเพิ่มความละเอียด)
และทั้งสองครั้งคือจุดที่แสดงว่าทีมวัดจริง

## กติกาภาษา — หัวข้อใช้ศัพท์อังกฤษทับศัพท์ได้ · บทพูดต้องเป็นไทยเสมอ (เพิ่ม 16 ส.ค. 2569 รอบที่ 4)

ยึดโครงหัวข้อจากสไลด์รุ่นพี่สองเด็ค (§1.7) — **ชื่อ "ส่วน" ระดับบนสุดทั้งหมดเปลี่ยนเป็นภาษาอังกฤษ**
ตาม TOC ของเด็ครุ่นพี่: Introduction / Framework / Literature Review / Model / Data Collection /
Model Training / Model Result / Web Application Demonstration / Tools & Technology / Conclusion
(รายละเอียดการแม็ปแต่ละส่วนอยู่ใน `Design systems/FINAL-CONTENT.md`) **หัวสไลด์ย่อย**ก็ใช้คำอังกฤษ
ทับศัพท์ได้เช่นกัน โดยเฉพาะศัพท์เฉพาะทาง/ชื่อเครื่องมือ/ชื่อ metric (เช่น `Confusion Matrix`,
`YOLO11n Architecture`, `Scope of Work`, `Infrastructure`, `References`) — ไม่ต้องบัญญัติศัพท์ไทยฝืน ๆ

**แต่บทพูด (speaker notes) ต้องเป็นภาษาไทยล้วนเสมอ ไม่มีข้อยกเว้น** — เนื้อหาบนสไลด์ (บนจอ) ก็ยังเป็น
ภาษาไทยเป็นหลัก มีแค่คำที่เป็นศัพท์เฉพาะ/ชื่อเครื่องมือ/ตัวเลข metric เท่านั้นที่เป็นอังกฤษได้ ไม่ใช่การ
แปลทั้งประโยคเป็นอังกฤษ

| Docker | ระบบมีไฟล์ Python กับโฟลเดอร์ static เท่านั้น · `pip install -r requirements.txt` แล้วรันได้เลย |
| WebSocket / Celery / Redis | งานเบื้องหลังมีทีละไม่กี่งาน · polling ให้ประสบการณ์เท่ากันโดยไม่ต้องมีบริการเพิ่ม |
| Google Colab | session หลุดกลางการฝึก 150 รอบ · ต้องอัปโหลดชุดข้อมูลใหม่ทุกครั้ง · เครื่องส่วนบุคคลควบคุมได้เต็มที่ |
| เช่า GPU ค้างไว้สำหรับ deploy | สกัดเฟรม / กำกับ / ส่งออก ไม่ได้ประโยชน์จาก GPU เลย · จ่ายเฉพาะตอนฝึกแล้วอัปโหลด `.pt` กลับเข้าระบบคุ้มกว่า |
| YOLO รุ่นใหญ่ (s / m / l) | VRAM 4 GB · รุ่น n ฝึกได้จริงในเวลาที่มี และเป็นรุ่นเดียวที่รันบน CPU ของโฮสต์ได้ในเวลาที่ยอมรับได้ |

## 6.4 วิธีเอาสองตารางนี้ขึ้นสไลด์

ตาราง 4 คอลัมน์เต็มจะแน่นเกินไปสำหรับจอโปรเจกเตอร์ — ให้แบ่งดังนี้:

- **บนสไลด์**: ตัดคอลัมน์ "ใช้งานยังไง" ออก เหลือ 3 คอลัมน์ (เครื่องมือ / ใช้ทำอะไร / ทำไมเลือก) ขนาด 11 pt
- **ในบทพูด**: คอลัมน์ "ใช้งานยังไง" คือสิ่งที่พูดออกเสียง
- **สไลด์สำรอง**: ตาราง 4 คอลัมน์เต็มไว้ตอบตอนถูกถามเจาะ

# §9 · คำสั่งสำหรับ Claude Code รอบถัดไป

1. **ไฟล์นี้คือ source of truth เดียวของกฎการออกแบบ** — ถ้าได้ตัวอย่างสไลด์เพิ่ม ให้ย่อยแล้ว
   **รวมเข้าที่ §1** ห้ามสร้างไฟล์ design system ใหม่แยกออกไป
2. **เขียนเนื้อหาลง `Design systems/FINAL-CONTENT.md`** ตามโครง §5 · แต่ละแผ่นมี: บนสไลด์ (คำต่อคำ) ·
   รูป · บทพูด · ที่มาตัวเลข · คำถามที่กรรมการน่าจะถาม
3. **ห้ามแต่งตัวเลข** ทุกตัวเลขต้องเปิดไฟล์ต้นทางเทียบ และต้องผ่านกติกา ❶-⓭ ใน §7
4. เมื่อผู้ใช้อนุมัติเนื้อหาแล้วจึงแปลงเป็น `deck/content.py` แล้วรัน
   `python build_deck.py && python verify_deck.py` ให้ผ่านสะอาดทั้งคู่
5. ถ้าเจอสไลด์ตัวอย่างที่น่าอ้างอิงแต่ดึงจากเว็บไม่ได้ **ให้บอกผู้ใช้เป็นลิงก์พร้อมเหตุผล**
   แล้วขอให้อัปโหลดไฟล์เข้ามา จากนั้นย่อยรวมเข้า §1
6. **ห้ามลืมสองข้อนี้ เพราะผู้ใช้ย้ำเป็นพิเศษ:**
   - **ส่วน W (workflow ต้นจนจบ) คือแกนกลางของเด็ค** ทุกส่วนถัดจากนั้นต้องบอกว่าตัวเองขยายขั้นไหนของผัง
   - **มุมมองคือนักศึกษานำเสนอต่ออาจารย์ที่เป็นกรรมการสอบ** (§2.5) — คุมสรรพนาม ระดับศัพท์
